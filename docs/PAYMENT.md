# 微信支付接入方案（全自动 · 赏金预付款 · 可提现）

> 目标：用户下单时**真实付款**，订单完成后钱结算给接单员，接单员**可提现到微信零钱**。
> 前提：后端必须迁到 CloudBase —— 支付回调要由云函数处理并直接改订单状态，
> 而 WorkBuddy Cloud 没有云函数、也不对外提供写库的服务端凭据。

## 一、资金流

```
① 发单付款
   用户点「支付 ¥N」→ 小程序调云函数 pay-create
   → 云函数用商户号+证书签名调 微信支付 JSAPI 下单
   → 返回 prepay_id → 小程序 wx.requestPayment 拉起收银台
   → 用户付款成功 → 微信回调 pay-notify（云函数验签）
   → orders.pay_status='paid'，进入待接单

② 完成结算
   发布方确认完成 → confirm_order_done
   → 云函数 settle 把「赏金 - 平台服务费」记账到接单员余额
   → 写 wallet_records（此时只是账，钱还在商户号）

③ 提现
   接单员申请提现 → 云函数 transfer
   → 调 微信支付「商家转账到零钱」
   → 直接打进接单员微信零钱（不需要他有商户号）
   → 回调确认 → wallet_records 记一笔支出
```

**关键点**：接单员不需要注册商户号，也不需要银行卡 —— 「商家转账到零钱」是
企业向个人付款的标准能力，学生用微信就能收。

## 二·补充 2：手续费与抽成（必须先定）

微信支付两个环节都收 **0.6%**：

| 环节 | 费率 | 谁承担 |
|---|---|---|
| 收款（用户付赏金） | 0.6% | 商户余额扣 |
| 提现（商家转账到零钱） | 0.6% | 商户余额扣 |

**算一笔账**（赏金 ¥10、平台不抽成的情况下）：

```
用户付 10.00 → 微信收 0.06 → 商户实际到账 9.94
平台转给接单员 10.00 → 另扣 0.06 手续费
平台净支出 10.06，净收入 9.94  →  每单亏 0.12（1.2%）
```

**所以「平台抽 0」是亏钱的。** 三个可选策略：

| 策略 | 用户付 | 接单员得 | 平台 |
|---|---|---|---|
| A. 平台抽 5% | 10.00 | 9.50 | +0.38 / 单 |
| B. 平台抽 2%（保本+微利） | 10.00 | 9.80 | +0.08 / 单 |
| C. 用户承担（赏金上浮） | 10.12 | 10.00 | 0（持平） |
| D. 提现手续费转嫁接单员 | 10.00 | 提现时扣 0.6% | 0（持平） |

**建议 A 或 B**：C 让用户多付钱很别扭；D 会让接单员觉得「到账少了」，不如一次性抽干净。

⚠️ 定下抽成后，`settle` 云函数的结算公式和前端「预计到手」文案都要跟着改，
所以**这个数要在写云函数之前定下来**。

## 二·补充 3：抽佣比例做成后台可调（✅ 已建表）

抽佣**不写死在前端**，存在 `pay_settings` 单行表里，超管在后台随时改，改完立刻对所有客户端生效。

| 字段 | 默认 | 含义 | 后台可调 |
|---|---|---|---|
| `commission_rate` | `0.05` | 平台抽佣比例（0–50%，超范围会被函数拒绝） | ✅ |
| `min_withdraw` | `10.00` | 提现门槛（低于这个数不让提） | ✅ |
| `withdraw_fee_rate` | `0.006` | 微信手续费率，**仅用于前端展示预估**，实际由商户余额扣 | ✅ |
| `enabled` | `false` | 在线支付总闸，没开通前前端不显示支付按钮 | ✅ |

**三个函数**：

```sql
get_pay_settings()                    -- 公开读，前端用它算「接单员预计到手」
calc_settle_amount(p_reward numeric)  -- 统一结算口径：返回 reward / commission / settle_amount
admin_update_pay_settings(...)        -- 超管改，带 0–50% 范围校验，NULL=不改
```

前端**必须调 `calc_settle_amount`** 而不是自己乘：
金额四舍五入的口径只有一处，避免出现「页面显示到手 9.50、实际入账 9.49」这种对不上账。

实测：`calc_settle_amount(10)` → `reward=10, commission=0.50, settle_amount=9.50` ✅

**后台入口规划**：等前端切换到 CloudBase 后，在「管理员工作台」加一页「支付设置」，
放这四个字段 + 一个「当前抽佣下，赏金 10 元接单员到手多少」的实时预览。

## 四、合规红线（重要，先看再决定）

平台「先收用户的钱、再转给接单员」这个动作，在监管口径里容易被视为
**二清（无证从事支付结算业务）**。规避方式不是技术问题，是业务定性问题：

1. **把服务定性为「平台自营」**：用户购买的是「平台提供的跑腿服务」，
   平台再向接单员支付**劳务报酬**。这样平台是服务提供方，不是资金通道。
2. **必须有真实的劳务关系证据**：接单员协议、任务记录、报酬明细，能对上账。
3. **不要做「余额长期沉淀 + 任意提现」**：那更像支付账户。建议提现设门槛
   （如满 10 元、T+1 到账），并在协议里写明是「劳动报酬结算」而非「账户余额」。
4. 校园场景单笔小、频次低，实际风险不高，但**正式运营前建议找学校法务/财务过一眼**。

## 五、云函数清单（迁库完成后开始写）

| 函数 | 触发 | 职责 |
|---|---|---|
| `pay-create` | 小程序调用 | 校验订单归属与金额 → 调 JSAPI 下单 → 返回支付参数 |
| `pay-notify` | 微信回调（HTTP） | 验签 → 幂等更新 `orders.pay_status` / `pay_txn_id` → 回 `{code:"SUCCESS"}` |
| `pay-query` | 小程序调用 | 主动查单兜底（回调丢了时补齐状态） |
| `settle` | 小程序调用 | 确认完成时计算实付 → 写 `wallet_records` |
| `transfer` | 小程序调用 | 提现：调商家转账到零钱 → 记录 `transfer_batch_id` |
| `transfer-notify` | 微信回调（HTTP） | 转账结果回调 |

## 六、需要新增的数据库字段 / 表

```sql
-- orders：支付状态与流水号
ALTER TABLE orders ADD COLUMN pay_status text NOT NULL DEFAULT 'unpaid';  -- unpaid/paid/refunded
ALTER TABLE orders ADD COLUMN pay_txn_id text;        -- 微信支付单号
ALTER TABLE orders ADD COLUMN paid_at timestamptz;
ALTER TABLE orders ADD COLUMN settle_amount numeric;  -- 实际结算给接单员的金额

-- 提现申请
CREATE TABLE withdraw_requests (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id text NOT NULL DEFAULT auth.uid(),
  amount numeric NOT NULL,
  status text NOT NULL DEFAULT 'pending',   -- pending/processing/success/failed
  batch_id text,                            -- 微信转账批次号
  fail_reason text,
  created_at timestamptz NOT NULL DEFAULT now(),
  finished_at timestamptz
);
```
